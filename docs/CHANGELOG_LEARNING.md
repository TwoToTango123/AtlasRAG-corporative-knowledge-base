# Журнал изменений для подготовки к собеседованию

Каждый пункт описывает одно изменение: что сделано, зачем и на какой вопрос
собеседования оно отвечает.

## 1. Репозиторий и .gitignore

- Проект положен в git, работа идёт в ветке `portfolio-polish`, каждый шаг в отдельном коммите.
- В `.gitignore` добавлены все варианты `.env.*` (кроме `.env.example`), индексы `.atlas_*`, кеш pytest, `results/raw/` с сырыми ответами модели.
- `.gitattributes` фиксирует переносы строк LF, чтобы diff не засорялся из-за Windows.
- Вопрос: «Как вы следите, чтобы ключи не утекли в репозиторий?» Ключ читается только из переменной окружения, файл `.env` в git не попадает, в репозитории лежит только шаблон.

## 2. Исправлен хеширующий эмбеддер

- `HashingEmbeddings` раскладывал токены по ячейкам через встроенный `hash()`. В Python 3 хеш строк солится случайно при каждом запуске (PYTHONHASHSEED), поэтому индекс от `cli.py ingest` не совпадал с векторами запросов в следующем процессе `cli.py ask`, и плотный поиск выдавал мусор.
- Теперь используется `hashlib.blake2b`, он детерминирован. Проверка: два отдельных процесса дают одинаковый вектор.
- Вопрос: «Какой баг вы нашли в своём проекте?» Хороший пример: в одном процессе всё работало, ломалось только после сохранения и загрузки индекса, поэтому сквозной тест в одном процессе ошибку не ловил.

## 3. Клиент Anthropic создаётся лениво

- Раньше `LLM.__init__` сразу требовал `ANTHROPIC_API_KEY`, и без ключа не работали даже `cli.py ingest` и обычный поиск, хотя LLM им не нужна.
- Теперь клиент создаётся при первом вызове модели. Индексация и поиск (вектор, BM25, RRF) работают без ключа, а `ask()` в самом начале явно проверяет ключ и падает с понятной ошибкой.
- Явная проверка нужна потому, что HyDE и реранкер глушат исключения и откатываются к обычному поиску: без неё эксперимент «с HyDE» без ключа тихо совпал бы с экспериментом «без HyDE».
- Вопрос: «Как устроены зависимости между компонентами? Можно ли тестировать поиск без LLM?» Можно, поиск полностью детерминирован и локален.

## 4. Режимы поиска, префиксы эмбеддеров, публичный `search()`

- В `Settings` добавлен `retrieval_mode`: `hybrid` (вектор + BM25 через RRF), `dense` (только вектор) или `sparse` (только BM25). Без этого нельзя измерить вклад каждой половины гибрида.
- У эмбеддеров появились `embed_queries` и `embed_documents`. Модели e5 и RoSBERTa обучались с префиксами (`query:`/`passage:`, `search_query:`/`search_document:`), и без них сравнение моделей было бы нечестным. Текст HyDE кодируется как документ, потому что он и есть «гипотетический документ».
- `AtlasRAG.search()` делает один раунд поиска без агента. У HyDE и реранкера есть счётчики сбоев, чтобы откат на обычный поиск было видно в отчёте, а не терялся молча.
- Вопрос: «Зачем гибрид, почему не только векторный поиск?» Теперь это проверяется абляцией (шаг 8), а не одними словами.

## 5. Поиск оценивается отдельно от генерации

- В `evaluation.py` добавлены recall@k, MRR и nDCG@k. Разметка задаётся в поле `relevant_sources`: пары «файл + дословная цитата с ответом». Чанк релевантен, если он из нужного файла и содержит цитату. Такая разметка переживает смену чанкинга, а id чанков нет.
- recall@k показывает долю нужных цитат в top-k (для многошагового вопроса нужно найти все части), MRR = 1/ранг первого релевантного чанка, nDCG@k — бинарный nDCG, который поощряет релевантные чанки выше в списке.
- Ответы оцениваются только на вопросах, у которых есть ответ. На вопросах `"answerable": false` считается доля честных отказов, а на остальных доля ложных отказов. Отказ определяется по флагу генератора `answer_found=false` (свойство `AnswerResult.refused`).
- Тесты `tests/test_retrieval_metrics.py` проверяют формулы на маленьких примерах, посчитанных вручную.
- Вопрос: «Если ответ неверный, как понять, кто виноват: поиск или генерация?» Если recall@5 низкий, нужного фрагмента не было в контексте, и виноват поиск. Если recall высокий, а корректность низкая, ошибается генератор.

## 6. База знаний расширена до 12 документов

- Добавлены 7 документов вымышленной Northwind Robotics, все тексты написаны с нуля: ИТ-FAQ (коды ошибок VPN), командировки, удалённая работа, онбординг, закупки, каталог комплектующих с артикулами, регламент выпуска обновлений.
- Документы ссылаются друг на друга, чтобы появились настоящие многошаговые вопросы: например, закупка у поставщика с персональными данными требует и регламента закупок, и политики безопасности.
- Специально оставлены «ловушки»: одинаковые фразы вроде «30 календарных дней» в разных контекстах, похожие сроки паролей (180 и 90 дней), SLA только для Enterprise.
- Итого 12 документов и 21 чанк. Корпус маленький, и это ограничение нужно называть честно: top-5 — это почти четверть базы.
- Вопрос: «На каких данных вы проверяли систему?» На синтетической базе, специально составленной под разные типы вопросов. Реальные внутренние документы никто бы не дал, а чужие тексты копировать нельзя.

## 7. Золотой набор: 39 вопросов с разметкой

- `examples/eval_cases.json`: 6 старых и 33 новых вопроса. По типам: факт (7), точный токен — код ошибки или артикул (7), многошаговый (8), перефразировка без общих слов (6), сравнение (5), без ответа в базе (6).
- У каждого вопроса есть `id`, `type`, эталонный `expected` и `relevant_sources` с дословными цитатами. У вопросов без ответа стоит `"answerable": false`, и среди них есть коварные: несуществующая модель NW-300 и SLA для тарифа Team, хотя SLA описан только для Enterprise.
- Тест `tests/test_eval_cases.py` проверяет, что каждая цитата реально лежит в каком-то чанке при текущем чанкинге. Иначе recall для такого вопроса никогда не дошёл бы до 1, и метрика молча врала бы.
- Вопрос: «Как вы строили тестовый набор и не подогнали ли его под систему?» Вопросы составлены по документам до запуска абляций, по типам из литературы о RAG. Слабость в том, что их писал автор системы, и это честно указано в README.

## 8. Скрипт абляций и первые реальные цифры

- `scripts/run_ablation.py` прогоняет золотой набор на шести конфигурациях (только вектор / только BM25 / гибрид RRF / гибрид + HyDE / гибрид + реранкер / полный агент) и на четырёх эмбеддерах. Результаты сохраняются в `results/ablation.json` (вместе с разбором по каждому вопросу) и `results/ablation.md`.
- Конфигурации с Claude без ключа не запускаются и помечаются «не измерено». Если LLM-шаг упал и сработал откат, это записывается в отчёт: цифры не подделываются ни в одну сторону.
- Главная находка: эмбеддер по умолчанию `bge-small-en-v1.5` англоязычный, на русском корпусе он даёт Recall@5 = 0.465, а гибрид с ним (0.813) хуже чистого BM25 (0.879). Плохая плотная половина тянет RRF вниз. Многоязычный `multilingual-e5-small` даёт гибрид с nDCG@5 = 0.883 против 0.610.
- Разница между e5-small и RoSBERTa (0.883 против 0.887) лежит внутри 95% бутстреп-интервала: на 33 вопросах победителя назвать нельзя. При этом e5-small меньше (118M параметров против 404M) и на CPU в несколько раз быстрее; задержка от прогона к прогону шумит, а метрики качества детерминированы.
- BM25 проваливает перефразировки (Recall@5 = 0.50), а нейросетевые эмбеддеры их вытягивают. Это и есть довод в пользу гибрида, теперь подкреплённый цифрами.
- Предупреждение `pooler.dense MISSING` у RoSBERTa безвредно: sentence-transformers использует свой слой пулинга, а не пулер HF.
- Вопрос: «Почему выбрали именно эту модель эмбеддингов?» Выбор по замеру на своём наборе, а не «по популярности». И честное ограничение: на маленьком наборе часть различий статистически незначима.

## 10. Эмбеддер по умолчанию сменён на multilingual-e5-small

- По результатам абляции (шаг 8) дефолт в `config.py` и `.env.example` сменён с `BAAI/bge-small-en-v1.5` на `intfloat/multilingual-e5-small`: на русском корпусе гибрид дал nDCG@5 0.883 против 0.610. RoSBERTa не хуже по качеству, но больше и медленнее.
- Нашлась ловушка: у обеих моделей размерность 384, поэтому старый индекс от bge прошёл бы проверку размерности и молча выдавал мусор. Теперь `meta.json` индекса хранит имя эмбеддера, и `load()` отказывается загружать индекс от другой модели.
- Тест `tests/test_index_persistence.py` проверяет, что после save/load поиск даёт те же результаты и что чужой индекс отклоняется.
- После смены дефолта абляция перезапущена: метрики совпали до знака, поменялась только строка, на которой меряются LLM-конфигурации (теперь e5-small).
- Вопрос: «Что будет, если поменять модель эмбеддингов в проде?» Нужна полная переиндексация: векторы разных моделей лежат в разных пространствах, и совпадение размерности ничего не гарантирует.

## 11. Мелкие хвосты: `cli.py ablate`, demo, зависимости

- Добавлена команда `python cli.py ablate`: все незнакомые флаги она передаёт в `scripts/run_ablation.py`, поэтому логика не дублируется. У остальных команд лишние флаги по-прежнему дают ошибку.
- `examples/demo.py` больше не печатает нули корректности для вопросов без ответа, а показывает, был ли честный отказ.
- `sentence-transformers` перенесён в обязательные зависимости: модель по умолчанию без него не работает, а молчаливый откат на хеширующий эмбеддер даёт заметно худший поиск (см. абляцию). Туда же добавлен `pytest`.
- Убрано предупреждение FutureWarning: в sentence-transformers 5.x метод получения размерности переименован, а код поддерживает оба имени.
- Вопрос: «Как воспроизвести ваши результаты?» Нужно выполнить `pip install -r requirements.txt` и `python cli.py ablate --skip-llm`. Метрики поиска детерминированы и совпадут до знака.

## 12. LLM-слой не привязан к провайдеру, по умолчанию Groq

- `llm.py` переписан: базовый класс `LLM` и два провайдера, `GroqLLM` (по умолчанию, модели gpt-oss через OpenAI-совместимый API) и `AnthropicLLM` (Claude, прежняя функциональность сохранена). Провайдер выбирается через `ATLAS_LLM_PROVIDER`.
- Главная сложность в том, что форматы tool use разные. У Anthropic вызов инструмента приходит блоком `tool_use` внутри `content`, а результат возвращается сообщением `user` с блоками `tool_result`. У OpenAI и Groq это поле `tool_calls` и отдельные сообщения с ролью `tool`. Агент теперь работает с нейтральными `ToolTurn`/`ToolCall`, а форматы переводит провайдер. Цикл агента покрыт офлайн-тестом на фейковом провайдере.
- Модели: `gpt-oss-120b` для агента и генерации, `gpt-oss-20b` для массовых задач (HyDE, декомпозиция, реранк, проверка обоснованности), судья `qwen3.8-27b` из другого семейства: судья той же модели склонен завышать оценки своим ответам.
- Базовый класс считает токены и сбои API и умеет кешировать ответы на диск. На бесплатном тарифе Groq лимит около 8 000 токенов в минуту, поэтому 429 — обычное дело: SDK повторяет запрос после `retry-after`, а кеш позволяет продолжить прерванный прогон.
- `config.py` теперь сам читает `.env`. README это обещал, но раньше `.env` нигде не загружался.
- Вопрос: «Почему вы не взяли LangChain для смены провайдера?» Нужны всего три операции (текст, JSON по схеме, шаг с инструментами). Своя тонкая обёртка на ~200 строк понятна целиком, и в ней видно, как на самом деле устроен tool calling у двух API.

## 13. Агент экономит токены: без повторов, с сигналом «нового нет»

- Первый живой прогон на Groq потратил 88 928 токенов на 2 вопроса. Агент на gpt-oss-120b игнорировал «будь экономным» в промпте: шесть раз искал «ФЗ-152», которого в базе нет, и дважды подряд повторил запрос `NW-300`.
- Правила перенесены из промпта в код. Повторный запрос (без учёта регистра и пробелов) не запускает поиск, агенту отвечают, что запрос уже был. В каждом результате поиска агент видит, сколько фрагментов действительно новые, а если новых нет, получает прямую подсказку заканчивать.
- Бюджет шагов снижен с 6 до 4: в промпте и так сказано, что большинству вопросов хватает 1–3 поисков. Каждый шаг стоит вызова HyDE и реранка, примерно 5 тысяч токенов.
- Абляция запускает агента первым из LLM-конфигураций и останавливается при первом сбое LLM, не записывая отчёт. Кеш при этом сохраняется, и следующий запуск продолжает с места остановки.
- Вопрос: «Как вы контролировали стоимость агентной системы?» Ограничения, которые важны для денег, задаются в коде, а не в промпте. Модель может проигнорировать инструкцию, а `if` нет.
