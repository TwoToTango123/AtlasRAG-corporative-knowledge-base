Проверено по коду и сохранённым результатам **7 ноября 2026 года**. Последняя проверка кода: **97 тестов прошли**. Новые платные прогоны при подготовке документа не запускались.

Здесь 120 вопросов с готовыми ответами от первого лица. Это широкий набор вероятных тем для AI/ML-стажировки; реальные уточнения зависят от интервьюера. Формулировки стоит понять и пересказать своими словами. Важно различать то, что реализовано, то, что проверено экспериментально, и дальнейшие планы.

## Как пользоваться материалом

1. Сначала проговори рассказ на две минуты без подсказки.
2. Выучи три истории: потерянный связующий документ, исправление цитат, ошибки оценщика.
3. Освой формулы Recall, MRR, nDCG, RRF и косинусного сходства.
4. Отрепетируй вопросы Q003, Q010, Q035, Q044, Q061, Q069, Q074, Q096, Q101 и Q108.
5. На незнакомое уточнение отвечай: «Этого я пока не измерял. Проверил бы так: …», затем предложи конкретный эксперимент.

В HTML есть поиск, фильтр приоритетных вопросов, случайный вопрос и раскрывающиеся ответы. Документ работает локально, без внешних запросов. Для печати ответы раскрываются автоматически.

Я изменил селектор контекста: он сохраняет опору исходного вопроса и лучший результат последнего поиска. На тех же 12 синтетических регрессионных задачах результат вырос с 10/12 до 12/12, Recall@5 — с 0,917 до 1,000.

Это гарантирует дословность выбранного текста, но не правильность вывода, поэтому семантическую поддержку проверял отдельно. Я также нашёл ошибки LLM-судьи и не трактую его оценки как истину. Это исследовательский прототип на небольшой демонстрационной базе, а не внедрённый корпоративный сервис.

## Рассказ на пять минут: логика подробного объяснения

**1. Задача.** Сотруднику нужно ответить по нескольким внутренним документам. Обычная LLM не знает актуальные правила компании, а поиск по ключевым словам не всегда понимает перефразировки. Я построил конвейер получения ответа из найденных источников. Бизнес-эффект, который можно проверять в будущем, — время поиска и число обращений к экспертам; коммерческого внедрения и измеренного ROI в проекте нет.

**2. Архитектура.** Текстовые документы разбиваются с учётом Markdown-заголовков и абзацев. Ориентир — 320 приблизительных токенов на чанк, overlap — 60. Это эвристика по символам, не строгая токенизация. Чанки индексируются BM25 и локальной E5. Векторное хранилище — NumPy в памяти, без внешней векторной БД. Для маленькой базы это помогает изучать качество без лишней инфраструктуры.

**3. Поисковая воронка.** Из каждого поискового индекса берётся до 12 кандидатов, RRF оставляет 10, реранкер — 5. При включённом HyDE гипотетический ответ используется только для векторного поиска, не как доказательство. Агент получает результаты инструмента, может переформулировать запрос и имеет бюджет четырёх поисковых вызовов. Финальная генерация отделена от планирования.

**4. Контроль качества.** Я разделил проверку на поиск, правильность ответа, поддержку фактов, дословность цитат и отказы. Основной демонстрационный набор — 39 вопросов, из них 33 ответимых и 6 без ответа. Чтобы действительно проверить последовательный поиск, добавлены 12 синтетических задач на корпусе из 84 документов, где нужно связать проект с актуальным нормативом. Эти наборы не являются независимой промышленной тестовой выборкой.

**5. Эксперименты.** Результат на обычных вопросах заставил усомниться в полезности постоянного агентного цикла: один поиск давал сопоставимую оценку правильности. На последовательных задачах агент был полезнее, но обнаружилась потеря уже найденной опоры при сборке финального контекста. Исправление проверялось на замороженных траекториях, чтобы изолировать селектор, а не одновременно менять поиск и генерацию.

**6. Исправления.** Селектор защищает опору исходной сущности и лучший результат последнего поиска; остальные места заполняются прежним ранжированием. Для цитат модель выбирает существующие единицы текста, а код копирует диапазон. Первый строгий вариант отклонял длинные допустимые диапазоны и оставлял часть ответов без цитат. Я сохранил этот результат и отдельно проверил разбиение диапазона на точные короткие части без потери слов.

**7. Вывод.** Главный результат проекта — понимание того, как локализовать ошибку RAG, а не просто получить красивый средний балл. Следующие содержательные шаги: новый корпус, независимые оценки, BGE внутри полного конвейера и передача результатов первого поиска агенту вместо повторного выполнения. Эти шаги пока не следует выдавать за реализованные.

## Карта архитектуры

```text
Индексация:
MD/TXT → загрузка → структурный чанкинг → локальные эмбеддинги E5 → NumPy-индекс
                                     └────────────────────────→ BM25-индекс

Один пользовательский вопрос:
[для диалога: уточнение → самостоятельный вопрос]
  → декомпозиция вопроса как подсказка агенту
  → планировщик LLM вызывает search(query, rationale)
      → [HyDE: гипотетический текст только для dense-поиска]
      → dense top-12 + BM25 top-12 → RRF top-10 → LLM-реранкер top-5
      → наблюдение агенту: первые 500 символов + оценки + число новых чанков
  → при необходимости следующий search, бюджет до четырёх вызовов
  → селектор anchored собирает финальный контекст
  → генератор LLM: ответ + ID и диапазоны цитат + answer_found + confidence
  → код проверяет ID/границы и материализует точные цитаты
  → вспомогательная LLM оценивает faithfulness, уверенность может снижаться
  → AnswerResult: текст, цитаты, предупреждения, оценки и trace
```

**Отдельно от ответа пользователю:** экспериментальный Qwen-оценщик, семантическая v2, NLI-бенчмарк и отчёты. Они не все включены в основной конвейер.

## Математический минимум

**Косинус:** cos(q,d) = (q·d)/(‖q‖·‖d‖). При L2-нормированных векторах равен скалярному произведению. Больше — ближе в выбранном пространстве, но не обязательно достаточно доказательств для ответа.

**BM25:** score(q,d) = Σ IDF(t) · tf(t,d)(k1+1) / [tf(t,d)+k1(1−b+b·|d|/avgdl)]. В коде k1=1,5; b=0,75; IDF(t)=ln[1+(N−df(t)+0,5)/(df(t)+0,5)]. Частоты насыщаются, а длина документа нормируется. Это лексический, а не нейросетевой поиск.

**RRF:** score(d)=Σ 1/(60+rank_i(d)), позиции с единицы. Документ на местах 1 и 10 получает 1/61+1/70≈0,03068. Нельзя складывать сырой BM25 с cosine без осмысленного преобразования шкал; RRF использует позиции.

**Recall@5 именно в этом проекте:** число уникальных найденных эталонных цитат / число эталонных цитат вопроса. Один чанк может покрыть несколько опор, а несколько перекрывающихся чанков — одну опору.

**MRR@5:** среднее 1/rank первого релевантного чанка; если в top-5 релевантного нет, вклад 0. Он не проверяет нахождение всех опор.

**nDCG@5:** DCG/IDCG; в коде бинарная релевантность чанка и DCG=Σ rel_i/log2(i+1). IDCG построен по числу релевантных чанков корпуса, а не числу уникальных опор. Поэтому overlap может влиять на nDCG; это не вторая версия Recall.

**Пример:** два релевантных чанка на позициях 1 и 5 дают Recall=1, MRR=1, nDCG≈(1+0,3869)/(1+0,6309)=0,850. Если найдена только первая из двух опор: Recall=0,5, MRR всё ещё 1.

**Поддержка фактов:** precision_supported=TP/(TP+FP), recall_supported=TP/(TP+FN). FP здесь — ошибочное подтверждение неподдержанного факта. Отвергать всё даёт FP=0, но recall=0; это не полезный проверяющий.

## Блок 1. Задача, вклад и выбор подхода

### Q001. Расскажите о проекте одним предложением

Я разрабатывал проверяемый RAG-ассистент по корпоративным документам: гибридный поиск и агент собирают источники, генератор отвечает с цитатами, а эксперименты отдельно проверяют поиск, поддержку фактов и поведение при нехватке данных.

### Q002. Какую бизнес-проблему вы решаете?

Сотруднику приходится искать правило среди инструкций, спецификаций и регламентов, иногда связывая несколько документов. Ассистент должен сократить этот путь и показать основание ответа. У меня демонстрационный прототип: реальную экономию времени, платящих пользователей и внедрение я не измерял.

### Q003. Что именно сделали вы и использовали ли ИИ для разработки?

Я разрабатывал проект с помощью ИИ-ассистента: использовал его для кода, экспериментов и разбора ошибок. На собеседовании могу объяснить архитектуру, проверки и ограничения. Я не утверждаю, что вручную написал каждую строку. Результат оцениваю по воспроизводимым артефактам и пониманию решений, а не по объёму сгенерированного кода.

### Q004. Чем RAG отличается от обычного обращения к LLM?

Перед генерацией RAG подбирает внешние документы и передаёт их модели как контекст. Это позволяет опираться на актуальную базу и ссылаться на источники без переобучения генератора. Однако поиск может ошибиться, модель может неверно применить правило, а источник может быть устаревшим: само наличие RAG не гарантирует правильности.

### Q005. Почему не fine-tuning на документах компании?

Для обновляемых фактов и прослеживаемых источников я выбрал поиск: документы можно переиндексировать без изменения весов. Fine-tuning можно отдельно использовать для поведения, формата или ранжирования, но в этом проекте модели не дообучались. Я не сравнивал качество и стоимость обученной модели с RAG, поэтому универсального превосходства не заявляю.

### Q006. Почему не загрузить все документы в большой контекст?

На базе из 12 документов это разумный baseline, и его стоило бы измерить отдельно. При росте базы полный контекст становится дороже, сложнее обновляется и содержит больше отвлекающих сведений. Мой прототип исследует выбор и сохранение релевантных опор; доказательства выигрыша над long-context baseline на большом корпусе у меня нет.

### Q007. Почему вообще агент, а не простой конвейер?

Для вопросов, где следующий запрос зависит от найденного идентификатора, одного поиска может не хватать. Например, сначала нужно узнать пакет проекта, затем найти его норматив. Но на обычных вопросах простой конвейер оказался сопоставим по качеству. Агент — инструмент для отдельных классов запросов, а не обязательное усложнение любого RAG.

### Q008. Что в проекте наиболее сильное технически?

Я бы выделил диагностику по этапам: удалось показать, что ошибка была после успешного поиска — при сборке контекста. Исправление проверялось на тех же траекториях. Второй пример — дословность цитат обеспечивается копированием диапазона кодом, а не надеждой, что модель аккуратно повторит текст.

### Q009. Где здесь машинное обучение, если модели готовые?

Я не обучал фундаментальную модель, а решал прикладную ML-задачу: выбирал эмбеддер, сравнивал ранжирование и генерацию, проверял разметку и утечки, анализировал ошибки и компромиссы. Это системная работа вокруг готовых моделей. Обучение собственного реранкера — возможное продолжение при наличии подходящих пар и независимой оценки.

### Q010. Это production-система?

Нет, это исследовательский прототип с CLI, Python API, тестами и воспроизводимыми экспериментами. Нет production HTTP-сервиса, разграничения прав на документы, нагрузочного SLA и подтверждённого бизнес-эффекта. Я могу показать, какие компоненты готовы, и перечислить конкретную работу для пилота, не выдавая планы за внедрение.

## Блок 2. Данные, чанкинг и эмбеддинги

### Q011. Какие данные и вопросы использовались?

Основная база — 12 Markdown-документов вымышленной компании, после чанкинга 21 фрагмент. Вопросов 39: 33 с ответами и 6 без ответа. Отдельно есть 12 синтетических последовательных задач на 84 документах. Эти числа описывают разные наборы; я не складываю их в один независимый промышленный benchmark.

### Q012. Как загружаются документы, поддерживаются ли PDF и OCR?

Загрузчик рекурсивно читает UTF-8 текстовые форматы: Markdown, TXT, RST и некоторые аналогичные расширения. Парсинг PDF, OCR и извлечение таблиц из сканов в проекте не реализованы. Для реальных данных добавил бы отдельный слой извлечения с сохранением страниц, таблиц и координат, а затем проверял потери информации до индексации.

### Q013. Как устроен чанкинг?

Сначала выделяются Markdown-разделы с сохранением заголовков. Крупные разделы делятся по абзацам, затем единицы упаковываются около целевого размера. Перекрытие переносит целые хвостовые единицы, если они помещаются в бюджет. Поэтому заголовки и абзацы меньше разрываются, но это не гарантированное окно ровно заданной длины.

### Q014. Почему размер 320 и перекрытие 60 токенов?

Это исходные параметры прототипа: баланс контекста фрагмента, точности поиска и объёма промпта. Они не объявляются оптимальными — полноценный sweep размеров не проводился. Более того, код считает приблизительные токены как длину текста/4; для русского языка и технических строк фактическая токенизация может заметно отличаться.

### Q015. Чанк никогда не превышает целевой размер?

Может превышать: если отдельный абзац длиннее бюджета, текущая упаковка не режет его дальше по токенам. Это известное ограничение. Я бы добавил tokenizer-aware разбиение с учётом границ предложений и таблиц, проверку максимума перед embedding и тест на очень длинный абзац, чтобы исключить незаметное усечение.

### Q016. Зачем overlap и каковы его недостатки?

Он помогает не потерять условие на границе фрагментов, но увеличивает индекс и может вернуть несколько почти одинаковых кусков. В текущем алгоритме overlap не обязан набрать ровно 60 токенов. Дубликаты также влияют на позиционные метрики; поэтому покрытие уникальных эталонных опор измеряется отдельно от релевантности чанков.

### Q017. Почему multilingual-e5-small?

Я сравнил варианты на русском демонстрационном корпусе. Англоязычный bge-small давал слабый поиск, а многоязычная E5 стала рабочей компактной моделью. E5-small выдаёт вектор размерности 384, считается локально и подходит для CPU-прототипа. Это выбор по нашему ограниченному набору, не заявление о лучшей модели вообще. [Карточка E5](https://huggingface.co/intfloat/multilingual-e5-small).

### Q018. Для чего префиксы query и passage?

Они задают роль текста для асимметричного поиска. В обёртке к запросам E5 добавляется `query: `, к документам — `passage: `. HyDE-текст тоже кодируется как документ. Сравнение без нужных префиксов могло бы искусственно ухудшить модель; правила зависят от конкретного эмбеддера. [Описание использования E5](https://huggingface.co/intfloat/multilingual-e5-small).

### Q019. Можно ли заменить эмбеддер без переиндексации?

Обычно нет: совпадение размерности не означает совпадение пространства. В проекте при загрузке проверяются имя эмбеддера в метаданных и размерность. Для другой модели нужно заново посчитать векторы. В более строгой версии я бы сохранял ещё revision, версию токенизатора и параметры подготовки текста, а не только имя.

### Q020. Что происходит без sentence-transformers?

В режиме auto есть детерминированный hashing fallback по словам и символьным триграммам; BM25 остаётся доступен. Это лексическая деградация, а не полноценная семантика. При явно выбранном sentence-transformers ошибка загрузки прерывает работу. Для честного сравнения нужно фиксировать backend, чтобы fallback не подменил исследуемую модель незаметно.

## Блок 3. BM25, dense, RRF и хранилище

### Q021. Как объясните BM25 без формулы?

Это поиск по словам с тремя идеями: редкое слово информативнее частого; повторения слова помогают, но не бесконечно; длинный документ не должен выигрывать просто из-за длины. В проекте токенизация — lowercase и Unicode-регулярное выражение. Лемматизации, полноценного inverted index и сложного анализатора русского здесь нет.

### Q022. Что означают k1 и b в BM25?

k1 управляет насыщением вклада частоты слова, b — нормировкой по длине документа. В реализации используются 1,5 и 0,75. Это стандартные стартовые значения, не результат оптимизации именно на нашей базе. При настройке я бы выбирал их на отдельной development-части и проверял на новых документах.

### Q023. Как работает dense retrieval?

Каждый чанк заранее превращается в нормированный вектор. Для запроса считаем такой же вектор и ищем близкие документы по косинусу. Это даёт семантические совпадения, но сходство не означает логическое следование. Чанк с похожей темой может не содержать нужной цифры, исключения или актуальной версии правила.

### Q024. Почему косинус сводится к dot product?

У нормированных векторов обе нормы равны единице, знаменатель косинусной формулы исчезает. Вектор запроса хранилище нормирует; документы приходят нормированными из провайдера эмбеддингов. Сам `VectorStore.add` не нормирует произвольный вход, поэтому этот контракт важен при добавлении нового backend.

### Q025. Почему использовать и BM25, и эмбеддинги?

BM25 хорошо использует точные слова и идентификаторы; dense помогает с перефразировками. Но гибрид не обязан улучшать каждую метрику: на нашем наборе dense E5 имел Recall@5 0,975, гибрид — 0,955, зато MRR и nDCG у гибрида были выше. Я проверяю компромисс, а не объявляю сумму методов автоматически лучшей.

### Q026. Как именно работает RRF?

Для каждого документа складывается 1/(60+позиция) по тем спискам, где он найден. Оценки BM25 и cosine напрямую не смешиваются, используются места. Сейчас веса списков одинаковые. Метод прост и устойчив к разным шкалам, но может ухудшать хороший рейтинг, если второй источник слабый; это наблюдалось с неудачным эмбеддером.

### Q027. Почему не нормировать два score и не сложить?

Так можно сделать, но преобразование и веса тоже требуют проверки: распределения меняются между запросами, а min-max зависит от набора кандидатов. Я выбрал RRF как простой baseline без обучения. Следующее сравнение должно использовать одинаковых кандидатов и отдельную выборку, а не подбирать веса по известным итоговым метрикам.

### Q028. Почему воронка 12 → 10 → 5?

Каждая поисковая ветка возвращает до 12 чанков, после RRF остаётся 10 кандидатов, после реранкера — 5. Это ограничивает стоимость парной оценки и размер контекста. Значения — параметры прототипа. Если нужного документа нет среди 10 кандидатов, реранкер его не восстановит, поэтому сначала нужно проверить candidate recall.

### Q029. Какая векторная БД используется и какова сложность?

Внешней БД нет: матрица NumPy и точный поиск по всем N векторам размерности d. Скалярные произведения стоят O(Nd), отбор кандидатов использует argpartition и сортировку выбранных. Это удобно для маленького корпуса, но измерений на миллионах документов нет. Для масштаба рассматривал бы ANN и фильтрацию по метаданным.

### Q030. Что знаете об ANN, HNSW и памяти индекса?

ANN ускоряет поиск за счёт приближённого соседства и требует измерять потерю recall. HNSW использует многоуровневый граф; в текущем проекте его нет. Сами float32-векторы занимают примерно N×d×4 байт: миллион векторов по 384 — около 1,54 ГБ без текстов, метаданных и индекса. Реальную пропускную способность нужно измерять.

## Блок 4. HyDE, реранкеры и модели

### Q031. Что такое HyDE?

Модель пишет гипотетический фрагмент, похожий по стилю на ответ, и его embedding помогает найти настоящие документы. Это поисковая подсказка, а не источник истины. В моей реализации складываются векторы вопроса и гипотетического документа, затем запрос нормируется в хранилище. Это конкретная вариация HyDE, а не дословное воспроизведение всех деталей статьи. [Статья HyDE](https://arxiv.org/abs/2212.10496).

### Q032. Если HyDE может выдумывать, почему это допустимо?

Его текст не включается в доказательства генератора и не индексируется как корпоративный документ. Он влияет на то, что будет найдено. Это всё равно риск смещения поиска к выдуманной конкретике, поэтому я сравнивал режимы с HyDE и без него. На нашем обычном наборе убедительного выигрыша не получилось.

### Q033. Доказали ли вы пользу HyDE?

Нет. В single-pass сравнении correctness по одному оценщику одинаков — 0,939, а Recall@5 с HyDE 0,985 против 1,000 без него. На маленьком наборе это не доказывает вред HyDE вообще. Практический вывод — не считать дополнительный LLM-вызов полезным по умолчанию и проверять по типам запросов.

### Q034. Зачем реранкер после embedding-поиска?

Первый поиск обеспечивает широкий набор кандидатов, а реранкер более внимательно сравнивает запрос с каждым текстом или со всем набором. Он может различить близкие по теме фрагменты и поставить содержащий ответ выше. Но он ограничен кандидатами и не заменяет ни проверку источника, ни семантический аудит готового ответа.

### Q035. Почему вы оставили LLM вместо специализированного реранкера?

LLM уже была встроена: одним batch-вызовом давала порядок, оценки 0–10 и причины для агента. BGE я тоже проверил: nDCG у него выше, Recall немного ниже; интервал разницы включает ноль. Поэтому доказанного победителя нет. Для замены нужно проверить ответы и поведение агента, а не просто подставить другую шкалу в старые эвристики.

### Q036. Чем bi-encoder отличается от cross-encoder?

Bi-encoder кодирует запрос и документ отдельно, поэтому документы можно индексировать заранее. Cross-encoder совместно обрабатывает пару и выдаёт оценку — дороже для всего корпуса, зато пригодно для небольшой выборки кандидатов. В проекте E5 используется на первом этапе, BGE проверялся как cross-encoder. [Документация Sentence Transformers](https://www.sbert.net/examples/cross_encoder/applications/README.html).

### Q037. Реранкер выдаёт score через attention?

Attention помогает токенам запроса и документа взаимодействовать внутри трансформера. Число релевантности выдаёт обученный выход модели, например классификационная голова, а не непосредственно attention matrix. Для BGE используются logits пар «запрос, фрагмент». У обычной LLM в нашем варианте оценка генерируется текстом по инструкции. [Карточка BGE](https://huggingface.co/BAAI/bge-reranker-v2-m3).

### Q038. Можно ли считать sigmoid(score) вероятностью полезности?

Sigmoid переводит logit в интервал 0–1, но сам по себе не калибрует его на нашей задаче. Нельзя автоматически заменить LLM-оценку 6/10 на BGE 0,6. Для решений о повторном поиске или отказе нужны отдельные размеченные данные, оценка precision/recall и подходящий порог. [Нормализация score BGE](https://huggingface.co/BAAI/bge-reranker-v2-m3).

### Q039. Какие модели использованы и какую роль они выполняют?

В RouterAI-прогонах основные модели — GPT-OSS 120B и DeepSeek V4.1 Flash; последующие опыты преимущественно с DeepSeek. GPT-OSS 20B обслуживает HyDE, декомпозицию, реранк и быструю самопроверку. Qwen3.8 27B — оценщик. Эмбеддинги — E5. При этом defaults обычного Settings по-прежнему выбирают Groq и GPT-OSS 120B: экспериментальная конфигурация задаётся отдельно.

### Q040. Как обоснуете выбор DeepSeek и можно ли обучить свой реранкер?

На первом небольшом прогоне DeepSeek был предпочтительнее по нескольким метрикам, но это один запуск, а оценки судьи позже пересматривались. Универсального сравнения моделей нет. Для собственного реранкера собрал бы пары query/document с hard negatives и отдельными источниками для теста; обучение и fine-tuning в этом проекте не выполнялись.

## Блок 5. Агентный цикл и сборка контекста

### Q041. Что именно делает агент?

Он планирует сбор данных: вызывает `search(query, rationale)`, читает результаты и при необходимости меняет запрос. Сам итоговый пользовательский ответ пишет другой шаг генерации. Декомпозиция отдельной вспомогательной моделью — подсказка, а не жёсткий список обязательных поисков. История вызовов сохраняется в RetrievalTrace.

### Q042. Как предотвращаете бесконечный цикл?

Есть бюджет четырёх tool-вызовов и нормализация повторов по lowercase и пробелам. Точный повтор не вызывает новый HyDE и реранк, но расходует счётчик. Семантически одинаковые перефразировки могут пройти: детектор не сравнивает смысл. Число новых чанков сообщается агенту, а решение об остановке в основном остаётся модельным.

### Q043. Когда агент останавливается и есть ли жёсткий порог релевантности?

Он может закончить без tool call или упереться в бюджет. Промпт советует ориентироваться на покрытие вопроса, новизну и оценки около 6. Это не детерминированный тест достаточности. Поле min_relevance_to_answer=5 в Settings объявлено, но основной конвейер не применяет его как жёсткий gate — я не стал бы утверждать обратное.

### Q044. Зачем нужны multi-hop задачи и как выглядит пример?

Вопрос спрашивает лимит проекта, но первая карточка хранит только код назначенного пакета. Его нужно извлечь и вторым поиском найти действующий норматив пакета. Без связки «проект → пакет» подходящая сумма сама по себе не доказательство. В наборе есть архивные версии, чтобы проверить актуальность, а не только совпадение числа.

### Q045. Как нашли ошибку, давшую улучшение 10/12 → 12/12?

Я сравнил все поисковые шаги с фактическим контекстом генератора. В двух неудачах нужные документы были найдены, но карточка проекта получила низкую оценку и выпала из общего top-5. Генератор обоснованно не мог установить пакет проекта. Это локализовало проблему в context selection, а не в embedding или способности модели рассуждать.

### Q046. Как работает anchored-селектор?

Он дедуплицирует найденные чанки, выбирает опору исходного вопроса по покрытию информативных слов и имён, защищает лучший результат последнего непустого поиска, затем заполняет остальные места прежним score-порядком. Дата убирается из идентифицирующих слов. Эталонные ответы и имена файлов как классы документов селектору не передаются. Это эвристика максимум двух опор, не универсальный графовый поиск.

### Q047. Почему не оставить просто самые высокие score всех поисков?

Оценки разных запросов не обязательно сопоставимы. Связующая карточка может не содержать ответную сумму и получить меньше, чем несколько очень похожих нормативов. На синтетических задачах это и привело к потере опоры. Селектор сохраняет нужный контекст, но может уступать по позиционным метрикам — этот компромисс отражён в отчётах.

### Q048. Что отличается у anchored и anchored_score?

Они отбирают тот же набор опор, но порядок разный: anchored оставляет защищённые опоры впереди, anchored_score сортирует выбранное по score. На 51 вопросе проверено равенство состава. Рост MRR на обычных вопросах не дал подтверждённого роста correctness, а на последовательных порядок по score ухудшал метрики. Поэтому anchored остался default.

### Q049. Почему полный контекст наблюдений сократил число поисков?

Агенту по умолчанию показываются первые 500 символов чанка, хотя генератор получает полный текст. Иногда ответное условие находилось дальше, и агент продолжал искать. В эксперименте с целыми наблюдениями среднее число поисков уменьшилось с 3,462 до 2,744, примерно на 20,7%. Это отдельная настройка, не новый default и не доказанная экономия всей стоимости.

### Q050. Поле trace.sufficient гарантирует достаточность доказательств?

Нет. В текущем коде оно устанавливается при завершении модельного цикла без инструментов; содержание доказательств детерминированно не проверяется. Если поисков вообще не было, выполняется прямой fallback. Для надёжного sufficient я бы определил явные требования к опорам и проверял покрытие, а не приравнивал остановку модели к истинности ответа.

## Блок 6. Генерация, цитаты и обоснованность

### Q051. Что возвращает генератор?

Структурированный ответ: текст, предложения цитат, answer_found и самооценку confidence. Код превращает допустимые предложения в Citation с source и координатами. Затем формируется AnswerResult с предупреждениями и trace. JSON-схема помогает контролировать формат, но не делает факты внутри JSON автоматически правильными.

### Q052. Почему свободные цитаты были проблемой?

Модель могла убирать Markdown, менять переносы, склеивать заголовок с пунктом или допускать опечатки. Иногда смысл сохранялся, но дословность терялась. В режиме free код проверял существование chunk_id, а текст цитаты не гарантировал. Я отдельно считал строгое совпадение символов и совпадение после нормализации, не называя все расхождения выдуманными фактами.

### Q053. Как формируются точные цитаты сейчас?

Исходник разбивается на существующие единицы U, модель возвращает chunk_id и начальную/конечную единицу. Код проверяет типы, ID и границы и копирует подстроку источника. В Citation сохраняются start_char/end_char. Поэтому выбранный текст не переписывается моделью; выбор подходящего диапазона всё ещё может быть семантически неправильным.

### Q054. Зачем unit_parts, если уже был режим units?

Первая строгая версия отклоняла любой диапазон длиннее 25 слов, даже с правильными координатами. Это оставило шесть обычных ответимых вопросов без цитат. Unit_parts разделяет допустимый длинный диапазон по существующим границам единиц, сохраняя все непробельные символы. Неверные ID и координаты по-прежнему отклоняются, а не исправляются догадкой.

### Q055. Что означает 97/97 и почему это не 100% правильности?

Это число материализованных цитат, посимвольно совпавших с источником в проверенном варианте. Длинный диапазон мог дать несколько цитат. Метрика не оценивает правильность всех фактов ответа и не доказывает, что выбранный текст поддерживает конкретный вывод. Для покрытия отдельно проверено наличие цитат у всех 45 ответимых вопросов набора.

### Q056. Может ли точная цитата поддерживать неправильный вывод?

Да. Источник «бизнес-класс только при полёте дольше шести часов и одобрении» можно процитировать точно, но ошибочно разрешить его для ровно шести часов. Координаты и текст при этом корректны. Нужна проверка чисел, строгих неравенств, отрицаний, условий, сущности и актуальной редакции, а не только string matching.

### Q057. Как проверяется faithfulness в основном приложении?

Вспомогательная LLM получает ответ и фактические источники, возвращает долю поддержанных утверждений и список неподтверждённых. При низкой оценке уменьшается confidence. Это модельная самопроверка, не доказательство. Основной быстрый аудитор не равен экспериментальной атомарной v2 и не заменяет автоматически ответ исправленным или гарантированно безопасным.

### Q058. Чем отличается семантическая проверка v2?

В ней отдельно извлекаются факты с вопросом и условиями, затем каждый проверяется по источникам как supported, contradicted или insufficient. Для положительного решения нужны существующие ID строк, которые код разворачивает в точные диапазоны. Вопрос помогает применять общее правило к сценарию, но не разрешает пользователю отменять корпоративную политику.

### Q059. Чем insufficient отличается от contradicted?

Contradicted требует явной несовместимости с правилом при тех же условиях. Insufficient означает, что сведений не хватает. Если температура эксплуатации не указана, нельзя ни подтвердить -40, ни автоматически утверждать, что устройство при -40 запрещено использовать. Условия и исключения могут делать случаи неоднозначными; спорные трактовки стоит фиксировать отдельно.

### Q060. Confidence 0,9 — это 90% вероятность правильного ответа?

Нет, это самооценка модели, дополнительно изменённая эвристиками. При answer_found=false или отсутствии допустимых цитат в unit-режиме она ограничивается 0,3; при низкой faithfulness может снижаться ещё. Калибровка на независимых данных не сделана. В интерфейсе такую цифру лучше не подавать как статистическую вероятность истины.

## Блок 7. Поисковые метрики и статистика

### Q061. Что именно означает Recall@5 в ваших отчётах?

Это покрытие уникальных эталонных цитат вопроса верхними пятью чанками. Чанк размечается через пару source и цитата, содержащаяся после нормализации. На multi-hop вопросе с двумя опорами одна найденная опора даёт 0,5. Это не доля правильных ответов и не обязательно классический recall по всем релевантным документам мира.

### Q062. Как считается MRR и чем он может обмануть?

Для вопроса берём обратную позицию первого релевантного чанка, затем усредняем. Первый релевантный на втором месте даёт 0,5. Если первая из двух нужных опор на первом месте, а вторая потеряна, MRR всё равно 1. Поэтому для последовательного ответа дополнительно нужны Recall и явная проверка обеих опор.

### Q063. Как считается nDCG в вашем коде?

Релевантные чанки получают бинарный gain, позиции дисконтируются через log2(rank+1), сумма нормируется на идеальный порядок релевантных чанков. Это измеряет удобство расположения, но не качество ответа. В отличие от Recall, здесь учитываются чанки, а не уникальные эталонные цитаты: перекрывающиеся фрагменты могут создавать избыточный gain.

### Q064. Приведите пример, где Recall одинаков, а nDCG разный

Если оба нужных чанка найдены, но занимают места 1 и 2, порядок идеален. Если места 1 и 5, Recall остаётся 1, MRR тоже 1, а nDCG около 0,85 при двух релевантных чанках. Но это ещё не значит, что LLM во втором случае ответит неправильно: влияние порядка нужно проверять генерацией.

### Q065. Что такое correctness, faithfulness и completeness?

Correctness — верность и соответствие вопросу/эталону, faithfulness — поддержка произнесённых фактов источниками, completeness — наличие всех нужных частей ответа. Ответ может быть верным по всем своим фактам, но не упомянуть исключение. И наоборот, он может случайно совпасть с эталоном, не имея достаточных опор в переданном контексте.

### Q066. Почему нельзя объединить все метрики в одну accuracy?

Они имеют разные единицы: вопросы, опоры, чанки, факты и цитаты. Даже 100% дословных цитат может получиться при маленьком числе принятых ссылок и плохом покрытии. Я сначала локализую стадию ошибки, а затем выбираю метрику. Если нужен единый критерий продукта, его нужно определить по последствиям ошибок и отдельно валидировать.

### Q067. Как оценивали вопросы без ответа?

В основном наборе их шесть. Проверялись корректный отказ и ложный отказ на ответимых вопросах. В коде refusal — флаг no_evidence или model_reports_answer_not_found. Это proxy: частичный ответ с таким флагом не всегда равен чистому отказу, поэтому я различаю машинный флаг и содержательный просмотр текста.

### Q068. Зачем bootstrap и почему парный?

Он оценивает неопределённость разницы на фиксированном наборе вопросов: многократно пересэмплируем вопросы и считаем метрику. Парный вариант сохраняет связь результатов методов для одного вопроса. Если интервал включает ноль, данных недостаточно для уверенного вывода о преимуществе. Это не доказательство равенства и не учёт всех источников стохастичности LLM.

### Q069. Почему 12/12 нельзя назвать 100% accuracy системы?

Это маленький синтетический регрессионный набор, использованный при разработке, и ответы просмотрены ассистентом. На нём изолирован конкретный дефект сборки контекста. Нет независимых компаний, большой выборки и человеческого holdout. На интервью я называю размер и происхождение набора вместе с результатом, а не переношу 12/12 на любые вопросы.

### Q070. Что не так со сравнением времени и средней стоимости запусков?

Сетевые паузы, rate limits, кеш, возобновления и включение оценщика в разные этапы делают старые средние несопоставимыми. Даже HyDE иногда выглядел быстрее без причины в самом алгоритме. Для честного latency-бенчмарка нужны одинаковые условия, отделённые cold/warm запуски, повторения и распределение задержек, а не один усреднённый проход.

## Блок 8. Оценщик, NLI и честность экспериментов

### Q071. Почему нельзя просто довериться LLM-as-a-judge?

Он ошибается и в фактах, и в применении критериев. У нас судья отверг правильные шесть месяцев испытательного срока и объявил существующий chunk_id вымышленным. Поэтому оценки — диагностический сигнал. Нужны исходные источники, детерминированные проверки ID/координат, контроли, разбор расхождений и независимая разметка для серьёзных выводов.

### Q072. Для чего оценщик из другой семьи моделей?

Это попытка уменьшить предпочтение собственных формулировок генератора. Но другая модель не становится автоматически независимым экспертом: общие ошибки, предвзятость эталона и плохие инструкции остаются. В новых аудитах скрывались названия моделей, методов и прежние баллы, передавались реальные источники; такие меры помогают, но не дают гарантии.

### Q073. Почему после нового оценщика баллы выросли без изменения ответов?

Изменились критерии и доступные судье данные, а в части проверок — сам проверяющий. Это изменение измерительного инструмента, не улучшение генератора. Я сохранял старые ответы и оценки и показывал их отдельно. Иначе можно было бы получить фиктивный прогресс, просто сменив промпт аудита.

### Q074. Кто размечал данные и есть ли независимый holdout?

Контроли и большая часть оценок подготовлены с ИИ-ассистентом. Позже по моему разрешению ассистент выполнил и пакет из 24 заданий; это не стало человеческой разметкой. У NLI были раздельные calibration/heldout разделы, но метки всё равно ассистентские. Нельзя называть результаты независимой оценкой промышленного обобщения.

### Q075. Как избегали утечки эталонов в ответы и проверки?

Генератор и селектор не получают expected/gold, оценки поиска считаются после результата. Для сравнения оценщика собственные метки и причины не передавались Qwen; extractor получал исходный ответ без готовой сегментации. При этом сами наборы известны разработчику, поэтому отсутствие прямой передачи меток не устраняет development-overfitting.

### Q076. Что делает NLI-модель и каковы результаты?

Она классифицирует пару «источник, утверждение» как entailment, contradiction или neutral. В локальном опыте mDeBERTa на 20 отложенных парах дала 18/20 по argmax, включая одну ложную поддержку. Строгий порог устранил положительные решения полностью: support recall стал нулевым. Это полезная диагностика, но не готовый production-фильтр.

### Q077. Почему entailment 0,996 всё равно могло быть ошибкой?

Softmax уверенно разделяет классы модели, но не гарантирует калибровку на наших правилах и числах. В опыте модель поддержала неправильный трёхмесячный срок для руководителя при шестимесячном правиле. Поэтому порог нельзя трактовать как автоматическую гарантию. Нужны проверка числовых условий, отдельная калибровка и анализ ошибок.

### Q078. Как выбирался порог NLI и почему результат плохой?

На 20 calibration-парах по заранее заданной сетке выбирался максимум recall при нуле false-supported. Чистое решение нашлось только при 1,0 — фактически reject-all на этих данных. На heldout support recall тоже 0. Нулевое число ложных подтверждений ценой отсутствия подтверждений не означает хорошей системы.

### Q079. Почему надо отделять извлечение фактов от их проверки?

Если extractor пропустил неудобное утверждение или потерял условие, verifier его уже не оценит. Можно получить высокий процент supported на неполном списке. Поэтому есть проверки на фиксированных фактах, отдельное извлечение из исходного ответа и сопоставление сегментаций. Число фактов — изменяемый знаменатель, а не объективная константа качества.

### Q080. Что показала последняя ассистентская разметка?

Qwen совпал с основными метками на 16/16 отдельных утверждений и 17/18 фиксированных фактов ответов. При альтернативных трактовках числа меняются. Qwen выделил 24 утверждения вместо 18: часть разницы — дробление, часть — повторения и сообщения об отсутствии цен. Это согласие с ассистентом, не независимая точность оценщика.

## Блок 9. Инженерия, стоимость и надёжность

### Q081. Как организован код и почему без тяжёлого agent-фреймворка?

Есть отдельные модули ingest, chunking, embeddings, retriever, reranker, agent, context, generator и evaluation; AtlasRAG их связывает. Свой небольшой цикл помогает видеть каждый вызов и ограничивать поведение. LangChain/LangGraph не используются в ядре этого проекта. При росте сложных workflow можно сравнить фреймворк, но он не заменит метрики и контракты.

### Q082. Что значит сменность компонентов в вашем случае?

Есть обёртка эмбеддингов и общий LLM-интерфейс; конфигурация поддерживает Groq, Anthropic и RouterAI. Некоторые компоненты всё ещё связаны напрямую: приложение создаёт конкретный Reranker и VectorStore. BGE лежит в отдельном классе и benchmark, а не уже полностью взаимозаменяемом production-переключателе. Следующее улучшение — явные протоколы и dependency injection.

### Q083. Как устроен кеш и что в его ключе?

Кешируются ответы LLM по хешу провайдера и параметров вызова: модель, сообщения, system, schema, max_tokens и другие аргументы. В RouterAI добавлена политика маршрутизации. Изменение промпта даёт другой ключ, поэтому не подмешивается старый ответ. Кеш — JSONL; на большие объёмы и конкурентность я бы выбрал другое хранилище.

### Q084. Чем кеш отличается от сохранения успешных кейсов?

Кеш сохраняет отдельный модельный вызов и помогает продолжить вопрос после сбоя. Case checkpoint хранит уже собранный результат задачи и позволяет не повторять её целиком. Оба слоя нужны для длинных опытов. Повторное использование кеша экономит вызовы, но делает результаты зависимыми — это нужно учитывать в latency и статистике повторений.

### Q085. Как контролируется бюджет?

RouterAI-адаптер перед вызовом получает тарифы и баланс, консервативно оценивает верхнюю стоимость и записывает резерв в общий ledger. Есть лимит 90 рублей на журнал и резерв остатка 10 рублей из исходных 100. При неоднозначной сетевой ошибке резерв остаётся. Это защита эксперимента; для одного журнала разрешён один процесс.

### Q086. Почему budget_used не равно реальному списанию?

В него могут входить консервативные резервы запросов, для которых сеть не дала достоверного финального статуса. Реальную стоимость сверяем с балансом и usage.cost, не стираем старый журнал ради продолжения. Последний сохранённый срез 04.11.2026: суммарно около 32,84 рубля с исходных 100. Это не текущий живой баланс и не цена одного production-запроса.

### Q087. Сколько LLM-вызовов у одного ответа?

Один поиск без HyDE обычно включает реранкер, генератор и faithfulness-аудитор — три основных вызова. HyDE добавляет один. Агент ещё вызывает декомпозицию и несколько ходов планировщика, а HyDE и реранкер повторяются для каждого нового поиска. Экспериментальный Qwen-судья оплачивается отдельно. Кеш и fallback меняют число свежих запросов.

### Q088. Как обрабатываются таймауты и rate limits?

Неоднозначный transport timeout не повторяется автоматически: он мог уже списать средства, резерв сохраняется. Подтверждённые ограничения частоты без списания имеют ограниченные повторы с паузами. Supervisor может позже возобновить незавершённые задачи из кеша. Ответы с upstream error и обрезанные structured outputs не объявляются успешными; диагностика сохраняется.

### Q089. Что проверяют 97 тестов?

В том числе метрики поиска, сохранение индекса, агентный цикл, отбор опор, точность диапазонов, работу семантических проверок, бюджетный адаптер и пакет разметки. Это число test cases pytest, не число независимых задач качества и не процент coverage. Моки API проверяют поведение кода, но не доказывают семантическую правильность реальной модели.

### Q090. Как хранится индекс, можно ли повторно загружать документы?

Индекс сохраняет матрицу vectors.npy, чанки JSONL и метаданные эмбеддера; после загрузки BM25 восстанавливается по чанкам. Полного versioned upsert/delete и безопасной инкрементальной переиндексации нет: повторное добавление может создать дубликаты. Для пилота нужны устойчивые идентификаторы версий, удаление старых чанков и согласованное переключение снапшотов.

## Блок 10. Масштабирование, безопасность и развитие

### Q091. Как превратить прототип в сервис?

Я бы выделил HTTP API, очередь индексации, версионированное хранилище документов, аутентификацию, ACL-фильтры и наблюдаемость. Затем измерил p50/p95, стоимость и качество на целевом корпусе и выбрал конфигурацию. FastAPI и Docker есть в других проектах резюме, но готовое такое развёртывание AtlasRAG сейчас не реализовано.

### Q092. Как гарантировать, что сотрудник не увидит закрытый документ?

В текущем прототипе ACL нет. В сервисе права должны фильтровать кандидатов на уровне поиска и доступа к исходникам до отправки в LLM; ссылка тоже должна проверяться. Нельзя считать ответ безопасным только потому, что модель попросили не раскрывать секреты. Кеши и traces тоже должны учитывать пользователя, tenant и версию прав.

### Q093. Есть ли защита от prompt injection в документах?

Документы нужно трактовать как недоверенные данные. Текущие инструкции и ограниченный инструмент не являются доказанной защитой от injection. У агента только поиск, но он всё ещё может исказить ответ или запрос. Для реального сервиса нужны тесты атак, изоляция инструкций, ограничения инструментов и независимые проверки, которых полностью в прототипе нет.

### Q094. Как учитывать новые и архивные версии регламентов?

В эксперименте нормативы содержат даты действия и отметки архивности, и я проверял, что агент выбирает актуальную редакцию через нужную опору. Детерминированного temporal-фильтра по метаданным нет. Для production добавил бы valid_from/valid_to, область действия и политику разрешения конфликтов, чтобы не полагаться только на чтение дат LLM.

### Q095. Что делать, если два источника противоречат друг другу?

Нужно выяснить версию, дату и область действия, показать противоречие и при необходимости отказаться от однозначного вывода. Сейчас универсального движка приоритетов документов нет. Я бы зафиксировал правила выбора источника и добавил сценарии с одинаковой датой, разными подразделениями и отсутствующими метаданными, а не просто брал самый высокий cosine.

### Q096. Что сейчас не доделано из обсуждавшихся улучшений?

Адаптивный режим «один поиск, потом агент» пока проверен ретроспективной симуляцией; переиспользование первой выдачи в реальном агентном цикле не реализовано. Нормализатор кодов остаётся экспериментом. BGE не подключён к полному агенту. Семантическая v2 не заменила основной faithfulness-аудит. Я называю эти пункты планами и экспериментами, а не выполненными функциями.

### Q097. Каким должен быть следующий эксперимент?

Я бы сравнил single-pass, полный агент и эскалацию с передачей первой выдачи без её повторного выполнения. Нужен новый набор с заранее выделенными одношаговыми, multi-hop и неответимыми вопросами. До запуска фиксируются правила маршрутизации, модели, версии, метрики и бюджет. Измеряются ответы, все опоры, отказы, p95 и реальная стоимость без оценщика.

### Q098. Почему адаптивная симуляция могла увеличить расход?

На последовательных задачах она сначала делала одиночный поиск, а затем выбирала сохранённый полный цикл агента, не переиспользуя первый результат. Поисков стало 3,833 вместо 2,833. На обычных вопросах счётчик уменьшился примерно на 25%. Это разные группы и proxy вызовов, а не измеренная денежная экономия готового маршрутизатора.

### Q099. Что показали вопросы с кодами без дефисов?

В локальном компонентном тесте Recall@5 гибрида снизился с 0,955 до 0,924. Восстановление уникальных кодов по документам вернуло метрику, но нормализатор не внедрён. На двух затронутых вопросах полный HyDE+rerank-конвейер и без него дал нужные опоры. Следовательно, ухудшение промежуточной метрики не доказало ошибку конечного ответа.

### Q100. Как измерили бы бизнес-пользу и качество на новых данных?

Собрал бы вопросы реальных пользователей с разрешёнными источниками и независимой разметкой, разделил по документам и времени. Для пилота измерял бы время решения, долю полезных ответов, ошибки с последствиями, правильные отказы и обращения к эксперту. Коммерческие цифры и SLA появились бы после такого измерения, а не из синтетического Recall.

## Блок 11. Неудобные уточнения и защита резюме

### Q101. Разве ваши 12/12 — не переобучение на тест?

Это действительно development-набор, поэтому я называю его регрессионным и не утверждаю независимого качества. Исправление важно тем, что причина ошибки локализована и проверена при неизменном поиске. Для вывода об обобщении нужен новый набор, замороженный до следующих изменений. Честная граница результата делает эксперимент содержательнее, чем просто красивый процент.

### Q102. 21 чанк — слишком мало, зачем такой сложный проект?

Согласен, на таком корпусе абсолютные метрики оптимистичны, а простой baseline обязателен. Я использовал маленькую базу для прозрачной диагностики и контроля API-расходов; отдельные последовательные задачи уже имеют 84 документа. Но масштабируемость на большой компании не доказана. Ценность проекта — исследование ошибок и воспроизводимые проверки, а не размер индекса.

### Q103. Гибрид хуже dense по Recall — почему вы это не скрыли?

Потому что это существенный результат: гибрид улучшал порядок, но терял часть покрытия. Метрика зависит от цели и типа вопросов. Я бы сравнивал candidate recall, top-k, перефразировки и технические коды, затем выбирал вариант под ограничения продукта. Фраза «гибрид всегда лучше» противоречила бы нашему же отчёту.

### Q104. Почему 100% supported по модели не закрывает задачу?

Проверяющий может пропустить условие, а extractor — не выделить ошибочный факт. Кроме того, полнота ответа не следует из поддержки произнесённых утверждений. В последнем разборе Qwen поддержал все 24 своих утверждения, но строгая ассистентская проверка нашла спорную область действия API и неполноту ответа об удалённой работе.

### Q105. Какая конкретная ошибка в коде или контракте ещё возможна?

Chunk ID строится из источника, ordinal и первых 64 символов текста: изменение более позднего фрагмента не обязательно меняет ID. Это не полноценная версия содержимого. Ещё есть приблизительный чанкинг и отсутствие upsert. Я могу показать эти места и предложить content hash, revision и тесты обновления, не выдавая текущие контракты за production-ready.

### Q106. Что будет при ошибке реранкера или неверной оценке?

При исключении LLM-реранкер возвращает первые кандидаты fusion и увеличивает счётчик ошибок. Код реранкера не обеспечивает полной валидации всех числовых оценок: нужны конечность, допустимый диапазон, уникальность ID и политика для пропусков. В платных экспериментах сбои дополнительно останавливаются адаптером/скриптами. Fallback поиска не превращает неудачный эксперимент в доказанно успешный.

### Q107. Какие данные видит агент и сохраняете ли вы chain-of-thought?

Агент видит вопрос, подсказку декомпозиции и наблюдения инструмента. В trace сохраняются запросы, краткие rationale, найденные чанки и выбранный контекст — это наблюдаемая траектория, не обещание доступа к внутреннему рассуждению модели. Для эксплуатации важно логировать действия и доказательства, а не считать текст объяснения гарантией причин решения.

### Q108. За этот AtlasRAG было второе место на чемпионате?

Нет. Второе место 2025 года в резюме относится к прежнему ассистенту для инженеров авиастроения. Текущий AtlasRAG — отдельный проект 2026 года, которым заменён первый проектный блок. Я не переношу награды, пользователей или результаты старого проекта на новый. Если интервьюер объединит их, сразу уточню это различие.

### Q109. Что вы сделали бы за неделю после прихода на стажировку?

Сначала уточнил бы целевую задачу, данные, baseline и критерии ошибок. Затем воспроизвёл бы существующую оценку, посмотрел несколько неудачных кейсов и выбрал одно локальное улучшение с проверкой. В своём проекте такой подход оказался полезнее, чем сразу добавлять ещё одного агента или менять большую модель без изоляции причин.

### Q110. Чего вы пока не знаете и почему вас стоит взять?

У меня нет подтверждённого опыта production RAG на большой закрытой базе и обучения фундаментальных моделей. Зато я могу разложить систему на проверяемые этапы, воспроизвести метрики, найти ошибку измерения и честно объяснить компромиссы. Для стажировки я хочу применить этот подход на реальных данных под техническим руководством и научиться доводить решение до эксплуатации.

## Блок 12. Диалог и базовая теория моделей

### Q111. Как обрабатывается уточнение «а у другой модели?»

Перед поиском Conversation.condense использует последние восемь пар вопрос/ответ и переписывает уточнение в самостоятельный вопрос. Например, «а у NW-200?» должно стать вопросом о нужной характеристике NW-200. Первый вопрос не переписывается. В шести проверенных сценариях сущность сохранялась, но это небольшой набор, а не общая оценка качества диалогов.

### Q112. Может ли ошибка прошлого ответа испортить следующий?

Да: история содержит и ответы ассистента, поэтому ошибочная сущность может перейти в переписанный запрос. История — средство разрешения отсылок, а не новый авторитетный источник политики. Для продолжения я бы проверял переписывание отдельно, сохранял исходный вопрос и тестировал неоднозначные уточнения. Сейчас в промпт берутся последние восемь ходов, но сам список turns безгранично растёт.

### Q113. Чем отличаются encoder и autoregressive decoder?

Encoder для embedding-задачи строит контекстные представления входного текста, которые затем агрегируются. Генерирующая autoregressive модель последовательно предсказывает следующий токен, учитывая доступный префикс; причинная маска не даёт заглянуть в будущие токены. В моём проекте эмбеддер работает локально, а генераторы вызываются через API. Архитектуру и веса этих моделей я не разрабатывал.

### Q114. Напишите формулу attention и объясните Q, K, V

Attention(Q,K,V)=softmax(QKᵀ/√d_k)V. Q — запросы токенов, K — ключи, V — значения; это обучаемые проекции скрытых представлений. Масштабирование помогает контролировать величину логитов, несколько голов дают несколько преобразований взаимодействия. Эти Q/K — матрицы внутри модели, не отдельные пользовательские поисковые запросы. Их веса нельзя напрямую назвать вероятностью истинности ответа. [Исходная статья Transformer](https://arxiv.org/abs/1706.03762).

### Q115. Как из представлений токенов получается embedding текста?

В опубликованном примере E5 используется усреднение последних скрытых состояний с маской, исключающей padding, затем L2-нормировка. В проекте это выполняет SentenceTransformer, а не самописный pooling. Способ агрегации зависит от модели: нельзя произвольно заменить mean на CLS и ожидать прежних свойств пространства без проверки. [Пример pooling E5](https://huggingface.co/intfloat/multilingual-e5-small).

### Q116. Что такое contrastive learning и hard negatives?

В простом варианте модель должна сблизить векторы связанной пары и отделить их от отрицательных примеров, используя similarity и обучающую функцию потерь. Hard negatives похожи по теме, но не отвечают на запрос: например, норматив другого пакета. Я не обучал такой эмбеддер; для собственного реранкера сначала нужны проверенные пары и защита от ложноотрицательных примеров.

### Q117. Что такое logits, softmax, temperature и почему ответы меняются?

Logits — ненормированные оценки вариантов. Softmax превращает их в распределение, а temperature меняет его резкость перед сэмплированием. Генерация может различаться между запусками и провайдерами. В текущих экспериментах нет доказательства полной детерминированности или контроля всех источников случайности. Кеш делает повтор payload воспроизводимым артефактом, но не заменяет независимые генерации для оценки разброса.

### Q118. Почему нельзя считать символы токенами и что при переполнении контекста?

Токенизация зависит от модели, языка и текста; 320 условных токенов по len/4 не гарантируют тот же размер у E5 или LLM. Нужно отдельно проверять лимиты embedding и генератора, оставлять место ответу и избегать тихого усечения важных условий. Контроль длины NLI-пар в эксперименте строгий, но универсального token-budget manager для всех компонентов нет.

### Q119. Что такое LoRA и где её можно было бы применить?

Это способ адаптировать модель через обучаемые низкоранговые добавки к матрицам вместо обновления всех исходных весов. Для этого проекта возможная задача — формат и поведение генератора либо специализированная оценка релевантности при наличии данных. LoRA не создаёт автоматически актуальные знания, источники и ACL. Обучение LoRA здесь не выполнялось, сравнения с ним нет.

### Q120. Можно ли считать проект полной реализацией CRAG из статьи?

Я бы говорил «корректирующий агентный поиск, вдохновлённый идеей CRAG». Здесь релевантность оценивает LLM, агент по инструкции может переформулировать запрос. Это не заявленная полная репродукция опубликованного метода с идентичными обучением и экспериментами. Нет отдельного внешнего web-поиска или доказанной калибровки достаточности. Термин описывает идею, конкретную реализацию я показываю в коде.

## Три истории по схеме «проблема → действие → результат → ограничение»

**История 1 — потерянная опора.** Агент находил карточку проекта и норматив, но top-5 оставлял только высоко оценённые нормативы. По trace видно, что ошибка после retrieval. Защитил опору исходной сущности и результат последнего шага. На тех же 12 траекториях: 10/12 → 12/12, ложные отказы 2 → 0. Ограничение: синтетические регрессии, только две защищённые опоры и возможный компромисс MRR на обычных вопросах.

**История 2 — хорошая дословность с плохим покрытием.** Строгий режим принял 43/43 точных цитаты обычных вопросов, но шесть ответимых вопросов остались без цитат: 14 допустимых диапазонов были слишком длинными. Сохранил исходный результат и отдельно сделал разбиение без потери слов. На всех 51 неизменных ответах получились 97/97 точных цитат и покрытие 45/45 ответимых. Ограничение: формат доказательства не равен правильности вывода.

**История 3 — оценщик ошибся.** Qwen присвоил правильному ответу нули, в другом случае объявил существующий ID вымышленным. Пересобрал фактический контекст, проверил ID и исходные payload-хеши, выделил проверку фиксированных фактов. Старые результаты не перезаписал. Ограничение: новый оценщик тоже ошибается, ассистентские метки не заменяют независимого человека.

## Мини-задачи у доски

### Задача A. Написать RRF и объяснить индекс позиции

```python
from collections import defaultdict

def rrf(rankings, k=60):
    scores = defaultdict(float)
    for ids in rankings:
        for rank, cid in enumerate(ids, 1):
            scores[cid] += 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

Каждый входной список должен содержать уникальные ID. При повторе одного ID внутри списка сначала нужна дедупликация. Формула использует позиции с единицы; параметр k здесь не число возвращаемых документов.

### Задача B. Написать покрытие опор и MRR

```python
def coverage_and_rr(ranked_ids, labels, n_gold, k=5):
    covered, first = set(), None
    for rank, cid in enumerate(ranked_ids[:k], 1):
        hits = labels.get(cid, set())
        covered.update(hits)
        if hits and first is None:
            first = rank
    recall = len(covered) / n_gold if n_gold else None
    rr = 1 / first if first is not None else 0.0
    return recall, rr
```

Это учебный вариант: для неответимого вопроса Recall здесь None, а в текущей функции проекта при нуле эталонов возвращается 0. В отчётах поиск агрегируется отдельно на ответимых случаях. Умение объяснить знаменатель важнее запоминания кода.

### Задача C. Проверить диапазон цитаты

```python
def exact_slice(text, start, end):
    if type(start) is not int or type(end) is not int:
        return None
    if not 0 <= start < end <= len(text):
        return None
    return text[start:end]
```

Почему `type(...) is int`, а не только isinstance? В Python bool — подкласс int. Почему не индексы байтов? Эти координаты считаются по Python-строке. Для JavaScript UTF-16 и UTF-8-байтов нужны явные преобразования; emoji нельзя считать одним и тем же числом единиц во всех представлениях. В проекте LLM выбирает номера единиц, а смещения вычисляет Python.

### Задача D. Объяснить верхнюю оценку API-вызовов

Если агент сделал S разных поисков с HyDE, поисковая часть содержит примерно 2S вызовов — HyDE и реранкер. Добавляются декомпозиция, T ходов планировщика, генератор и faithfulness: около 2S+T+3. Это бухгалтерская модель без кеша, повторов и внешнего судьи, а не точное обещание числа запросов. S и T не обязаны совпадать: один ход может возвращать несколько tool calls.

4. **Вопрос без ответа:** можно ли прийти в офис с собакой. Объяснить разницу отсутствия политики и запрета.
5. **Регрессия:** старый и новый отбор на тех же найденных чанках.

Сначала используй сохранённые результаты: демонстрация не должна зависеть от сети и баланса. Живой API-запуск при необходимости проведи отдельно, с проверенной конфигурацией, а не через полный старый benchmark.

```powershell
# Проверка кода без новых платных RAG-прогонов
.\.venv\Scripts\python.exe -m pytest -q

# Индексация демоданных: локальный эмбеддер может потребовать загрузки весов
.\.venv\Scripts\python.exe cli.py ingest examples/sample_docs

# Живой вопрос: используется настроенный провайдер, возможны платные API-вызовы
.\.venv\Scripts\python.exe cli.py ask "Что означает код E-401?"
```

Не открывай .env, полный ledger или сырые API-диагностики при публичном показе экрана. Обычный CLI и скрипты оплачиваемого эксперимента могут использовать разные настройки; защиту, которая включена в одном адаптере, нельзя автоматически приписывать любому провайдеру.

## План повторения и вопросы интервьюеру

**За 20 минут:** рассказ на две минуты → история потерянной опоры → Recall/MRR/nDCG → Q003, Q035, Q069, Q074, Q096, Q108. **За вечер:** пройти все блоки, написать RRF и exact_slice без подсказки, найти в коде каждую настройку из паспорта.

Попроси собеседника сыграть интервьюера: «Задай пять уточнений к моим цифрам, одно к безопасности, одно к роли ИИ в разработке». Если на ответ нужен отчёт, нормально сказать: «Точное значение сейчас не воспроизведу, но определение и метод проверки такие…».

Полезные вопросы команде: какие ошибки RAG для вас критичнее; кто размечает данные; как устроены права на документы; какие есть baseline и latency/budget-ограничения; как стажёр получает обратную связь по экспериментам.
