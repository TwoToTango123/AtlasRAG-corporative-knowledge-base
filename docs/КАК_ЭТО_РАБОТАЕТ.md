# Как работает AtlasRAG — объяснение с нуля

Этот документ — подробное объяснение каждого компонента системы **для человека,
который ничего не знает о RAG**. Здесь нет требования знать машинное обучение.
Будут аналогии, простые примеры и разбор каждого файла: что он делает, зачем
нужен и как связан с остальными.

---

## Часть 1. В чём вообще проблема?

Представьте, что у компании есть сотни документов: регламенты, инструкции,
договоры, спецификации. У сотрудника возникает вопрос: «Какое у нас окно
возврата для корпоративных клиентов?». Варианты:

1. **Спросить у коллеги** — медленно, коллега может ошибиться или быть занят.
2. **Искать вручную** (Ctrl+F по словам) — находит только точные слова. Если в
   документе написано «срок возврата», а вы ищете «окно возврата», поиск может
   ничего не найти.
3. **Спросить у обычного чат-бота (ChatGPT и т.п.)** — он не знает внутренних
   документов вашей компании. Он либо честно скажет «не знаю», либо —  что хуже —
   **выдумает** правдоподобный, но неверный ответ. Это называется
   **галлюцинация**.

### Что такое RAG?

**RAG = Retrieval-Augmented Generation** = «генерация с дополнением через поиск».
Идея в двух шагах:

1. **Retrieval (поиск)**: по вопросу пользователя сначала **находим** в базе
   документов те фрагменты, которые относятся к делу.
2. **Generation (генерация)**: отдаём эти найденные фрагменты языковой модели
   (Claude) и просим: «Ответь на вопрос, опираясь ТОЛЬКО на эти фрагменты».

Аналогия: это как студент на экзамене с **открытой книгой**. Он не обязан помнить
всё наизусть (и не выдумывает) — он быстро находит нужную страницу и отвечает по
ней. RAG превращает «всезнайку, который иногда врёт» в «эксперта, который сначала
сверяется с документами».

### Что такое «агентный» RAG (это и есть наша система)?

Обычный («наивный») RAG делает поиск **один раз**: взял вопрос → нашёл top-N
фрагментов → отдал модели. Это плохо работает, когда:
- вопрос **составной** («какой лимит API *и* какая компенсация при сбое SLA?» —
  это два разных факта в двух разных документах);
- первый поиск нашёл **мусор**, и система этого не заметила.

**Агентный RAG** даёт самой модели Claude управлять поиском, как живому
исследователю: она может искать **несколько раз**, **переформулировать** запрос,
**оценивать** качество найденного и сама решать, когда данных достаточно. Именно
это — главная «фишка» AtlasRAG.

## Часть 2. Из чего состоит система (общая карта)

> Ниже «Claude» означает языковую модель вообще. Система написана так, что
> модель можно сменить: по умолчанию теперь используется Groq (`gpt-oss-120b`
> для рассуждений, `gpt-oss-20b` для массовых задач), а Claude подключается
> через `ATLAS_LLM_PROVIDER=anthropic`.

Когда пользователь задаёт вопрос, он проходит такой путь:

```
   ВОПРОС
     │
     ▼
 [1] ПЛАНИРОВЩИК ЗАПРОСОВ  — раскладывает вопрос на части, придумывает
     (query_planner.py)      гипотетический ответ (HyDE) для лучшего поиска
     │
     ▼
 [2] ПОИСКОВЫЙ АГЕНТ  — мозг системы. В цикле решает, что искать, читает
     (agent.py)         оценки, переформулирует, решает когда хватит
     │   (на каждый поиск вызывает ↓)
     ▼
 [3] ГИБРИДНЫЙ ПОИСК  — ищет двумя способами сразу и объединяет результаты
     (retriever.py)      ├─ векторный поиск (vector_store.py + embeddings.py)
     │                   └─ ключевой поиск BM25 (bm25.py)
     ▼
 [4] РЕРАНКЕР + ОЦЕНЩИК  — Claude оценивает каждый фрагмент от 0 до 10
     (reranker.py)          (это и есть «корректирующий RAG» / CRAG)
     │
     ▼  (агент собрал достаточно фрагментов)
 [5] ГЕНЕРАТОР  — Claude пишет ответ ТОЛЬКО по найденным фрагментам,
     (generator.py)   с дословными цитатами-ссылками
     │
     ▼
 [6] ПРОВЕРКА ДОСТОВЕРНОСТИ  — второй проверяющий Claude: «а ответ точно
     (generator.py)            подкреплён фрагментами?» (анти-галлюцинация)
     │
     ▼
   ОТВЕТ + ССЫЛКИ + УВЕРЕННОСТЬ
```

А ещё до всего этого документы нужно один раз **загрузить и проиндексировать**
(`ingest.py`, `chunking.py`). Разберём всё по порядку.

## Часть 3. Подготовка базы знаний (происходит один раз)

### 3.1. Загрузка документов — `ingest.py`

**Задача:** взять папку с файлами (`.md`, `.txt` и т.п.) и прочитать их в память.

Простыми словами: программа обходит папку, открывает каждый текстовый файл и
складывает его содержимое в объект `Document` (текст + откуда он взят). Ничего
сложного — это «дверь», через которую ваши документы попадают в систему.

### 3.2. Нарезка на фрагменты («чанкинг») — `chunking.py`

**Задача:** разрезать длинный документ на小 небольшие куски — **чанки** (chunks).

**Зачем?** Нельзя искать «по целому документу» — он слишком большой, и в ответ
попало бы много лишнего. Нужны небольшие самодостаточные кусочки (примерно один
раздел или несколько абзацев). Тогда поиск вернёт именно нужный абзац, а не
30-страничный регламент целиком.

**Как это сделано умно:** мы режем не «каждые 500 символов подряд» (так можно
разорвать предложение посередине), а **по структуре** — сначала по заголовкам
Markdown (`##`), потом по абзацам. Куски делаются с небольшим **перекрытием**
(overlap): конец предыдущего чанка повторяется в начале следующего. Это чтобы
факт, оказавшийся на границе двух кусков, не потерялся.

Аналогия: вы не рвёте книгу на случайные обрывки — вы аккуратно копируете её по
главам и абзацам, слегка внахлёст.

### 3.3. Превращение текста в числа («эмбеддинги») — `embeddings.py`

Это ключевая идея, на которой держится «умный» (семантический) поиск.

**Проблема:** компьютер не понимает смысл слов. Для него «отпуск» и «отгул» —
просто разные наборы букв.

**Решение — эмбеддинг (embedding):** специальная модель превращает каждый кусок
текста в **вектор** — длинный список чисел (например, 768 чисел). Магия в том,
что тексты с похожим **смыслом** получают **похожие** векторы, даже если слова
разные. «Сколько дней отпуска» и «продолжительность ежегодного отдыха» окажутся
рядом в этом «пространстве смыслов».

Аналогия: представьте огромную карту, где каждый текст — точка. Тексты про
отпуска лежат в одном районе карты, про безопасность — в другом. Чтобы найти
ответ, мы ставим точку-вопрос и смотрим, какие точки-документы оказались рядом.

**Две реализации в нашем коде:**
- `SentenceTransformerEmbeddings` — настоящая нейросеть для эмбеддингов
  (рекомендуется, нужно `pip install sentence-transformers`). Даёт честный
  семантический поиск.
- `HashingEmbeddings` — простой **запасной** вариант без всяких зависимостей
  (работает офлайн). Он опирается на буквы и слова (лексический), а не на
  глубокий смысл, но позволяет всей системе работать «из коробки».

> ⚠️ Тонкость, которую мы специально учли: токенизатор (то, что делит текст на
> слова) использует Unicode-шаблон `\w+`, поэтому он понимает **и латиницу, и
> кириллицу**. Если бы стоял шаблон «только a-z», русский текст вообще не
> индексировался бы.

### 3.4. Хранилище векторов — `vector_store.py`

**Задача:** хранить все векторы чанков и быстро находить «ближайшие» к вектору
вопроса.

Простыми словами: это записная книжка, где для каждого чанка записан его вектор.
Когда приходит вопрос, его тоже превращают в вектор, и хранилище возвращает чанки
с **самыми похожими** векторами. «Похожесть» считается через **косинусную меру**
(насколько два вектора «смотрят в одну сторону»). Мы заранее нормализуем векторы,
поэтому сравнение — это одно быстрое умножение матриц (через библиотеку numpy).

Хранилище умеет сохраняться на диск (`save`) и загружаться (`load`), чтобы не
индексировать документы заново при каждом запуске. В больших проектах сюда
поставили бы специализированную базу (FAISS, pgvector) — но интерфейс тот же.

### 3.5. Ключевой поиск BM25 — `bm25.py`

**Задача:** искать по **точным словам**, а не по смыслу.

**Зачем, если уже есть эмбеддинги?** Потому что у смыслового поиска есть слепое
пятно: **редкие точные токены** — артикулы (`NW-200`), коды ошибок (`E-409`),
имена, номера. Смысловой поиск может «размазать» их, а вот старый добрый поиск по
словам найдёт точное совпадение мгновенно.

**BM25** — это классический, проверенный десятилетиями алгоритм поиска по
ключевым словам (на нём построены поисковики и Elasticsearch). Грубо говоря, он
оценивает: насколько редкое слово из запроса встречается в данном документе и как
часто. Чем реже слово в целом и чаще в конкретном документе — тем выше балл.

## Часть 4. Как происходит поиск ответа (на каждый вопрос)

### 4.1. Планировщик запросов — `query_planner.py`

Перед поиском Claude помогает «понять» вопрос двумя приёмами:

**Декомпозиция (разбиение).** Если вопрос составной — «какой лимит API *и* какая
компенсация при сбое?» — планировщик разбивает его на отдельные под-вопросы.
Каждый под-вопрос потом ищется отдельно. Это резко повышает шанс найти всё.

**HyDE (Hypothetical Document Embeddings — «гипотетические эмбеддинги
документа»).** Звучит сложно, идея простая: вместо того чтобы искать по короткому
вопросу, мы просим Claude **придумать**, как мог бы выглядеть ответ (2-3
предложения, факты можно выдумать). Затем ищем похожее на этот «выдуманный
ответ». Почему это работает? Потому что настоящий абзац-ответ в документе по
форме и словам ближе к развёрнутому ответу, чем к короткому вопросу. Этот
выдуманный текст нигде не показывается — он только «наводит прицел» поиска.

### 4.2. Поисковый агент — `agent.py` (СЕРДЦЕ СИСТЕМЫ)

Здесь происходит главное отличие от обычного RAG. Мы даём Claude **инструмент**
под названием `search` и говорим примерно так:

> «Твоя задача — собрать достаточно данных, чтобы можно было ответить. Ты сам
> решаешь, что искать. Каждый результат поиска приходит с оценкой релевантности
> 0–10. Если результаты слабые — переформулируй запрос и поищи снова. Когда
> данных достаточно — остановись.»

Это называется **цикл с использованием инструмента** (tool-use loop). Claude:
1. думает и вызывает `search("окно возврата enterprise")`;
2. получает фрагменты с оценками;
3. читает: «оценки высокие, но про корпоративных клиентов мало» → вызывает
   `search` ещё раз с уточнением;
4. когда уверен, что собрал всё, — пишет короткую заметку «нашёл, данных
   достаточно» и останавливается.

Аналогия: это не библиотекарь, который молча приносит первые 5 книг с полки. Это
**исследователь**, который ищет, смотрит на качество найденного, при необходимости
ищет иначе и сам понимает, когда пора остановиться.

Важно: агент **не пишет финальный ответ** — он только **собирает доказательства**
(фрагменты). Ответ напишет отдельный шаг (генератор). Такое разделение делает
каждый этап простым и проверяемым.

Весь путь поиска записывается в «трассу» (`RetrievalTrace`) — можно увидеть,
какие запросы делал агент и что нашёл. Это важно для **прозрачности**: видно, на
чём основан ответ.

### 4.3. Гибридный поиск и объединение рангов (RRF) — `retriever.py`

Когда агент вызывает `search`, под капотом запускаются **оба** поиска сразу:
- смысловой (векторный) — ловит перефразировки;
- ключевой (BM25) — ловит точные слова.

Теперь надо **объединить** два списка результатов. Проблема: их «баллы»
несравнимы (косинус 0.83 и BM25-балл 7.2 — это про разное). Решение —
**Reciprocal Rank Fusion (RRF)**: мы смотрим не на баллы, а на **места в
рейтинге**. Если документ был 1-м в смысловом поиске и 3-м в ключевом — он
получает хороший суммарный балл по формуле `1/(k + место)`. Документы, которые
высоко в *обоих* списках, всплывают наверх.

Аналогия: два эксперта составили свои топ-10. RRF — это способ честно свести два
их мнения в один итоговый список, не пытаясь сравнивать их «оценки в баллах»
напрямую.

### 4.4. Реранкер и оценщик CRAG — `reranker.py`

После гибридного поиска у нас, скажем, 10 кандидатов. Они отсортированы грубо.
Теперь **сам Claude** читает запрос и каждого кандидата и выставляет оценку
релевантности **0–10** с короткой причиной. Это:
- **реранкинг** — пересортировка кандидатов по реальной полезности (оставляем
  топ-5);
- **CRAG (Corrective RAG, «корректирующий RAG»)** — те же оценки говорят агенту,
  хороший ли был поиск. Если всё набрало мало баллов — агент поймёт, что нужно
  переформулировать запрос.

Всё это делается **одним** вызовом модели для всех кандидатов сразу (быстро и
дёшево), причём на быстрой модели (по умолчанию `gpt-oss-20b`).

Аналогия: гибридный поиск — это стажёр, принёсший стопку из 10 потенциально
полезных бумаг. Реранкер — это эксперт, который быстро просматривает их и говорит:
«вот эти 3 — в точку (9/10), а эти 7 — мимо».

### 4.5. Генератор ответа — `generator.py`

Теперь у нас есть лучшие фрагменты. Генератор передаёт их Claude с жёсткой
инструкцией:

> «Ответь на вопрос, используя ТОЛЬКО эти фрагменты. Каждую мысль подкрепи
> ссылкой: укажи id фрагмента и **дословную цитату** из него. Если ответа в
> данных нет — так и скажи и поставь низкую уверенность. Отвечай по-русски.»

Чтобы ответ всегда был в строгом машинно-читаемом виде, используется
**структурированный вывод**: Claude обязан вернуть JSON по заданной схеме —
`{ ответ, ссылки: [{chunk_id, цитата}], найден_ли_ответ, уверенность }`. Это
избавляет от хрупкого «выдёргивания» данных из свободного текста.

Затем код **проверяет ссылки**: каждая цитата должна ссылаться на реально
существующий фрагмент. Выдуманные ссылки отбрасываются.

### 4.6. Самопроверка достоверности — `generator.py` (`faithfulness`)

Финальный страж от галлюцинаций. Берём готовый ответ и фрагменты и спрашиваем
**другого** Claude: «Какая доля утверждений в этом ответе реально подтверждается
этими фрагментами? Дай оценку 0–1 и перечисли неподтверждённое».

Если обоснованность низкая — система **снижает уверенность** в ответе и добавляет
предупреждение. То есть система способна сказать «я не уверена», вместо того чтобы
уверенно ошибаться. Для бизнеса это критично: лучше честное «не знаю», чем
красивый неверный ответ.

Аналогия: это редактор-фактчекер, который сверяет каждое предложение готовой
статьи с источниками, прежде чем её опубликовать.

## Часть 5. Дополнительные возможности

### 5.1. Память диалога — `memory.py`

Позволяет вести **многоходовый** разговор. Пример:
- Вы: «Сколько отпуска после 6 лет?» → ответ.
- Вы: «А у подрядчиков так же?»

Второй вопрос сам по себе непонятен («так же» — как что?). Память берёт историю и
**переписывает** его в самостоятельный: «Накапливают ли подрядчики отпуск так же,
как сотрудники с 6-летним стажем?». Уже по такому вопросу поиск отработает верно.

### 5.2. Оценка качества — `evaluation.py`

Как понять, что система вообще хорошо отвечает? Нельзя улучшать то, что не
измеряешь. Здесь есть **тестовый набор** (`examples/eval_cases.json`) — список
вопросов с эталонными ответами. Система прогоняет их все, и **судья-LLM**
выставляет три оценки:
- **корректность** — совпал ли ответ с эталоном;
- **обоснованность** — не выдумано ли (из проверки достоверности);
- **качество ссылок** — есть ли ссылки и по делу ли они.

Это «приборная панель», по которой можно безопасно менять настройки (чанкинг,
промпты) и видеть, стало лучше или хуже.

**Поиск оценивается отдельно, без LLM.** У каждого вопроса в наборе указаны
`relevant_sources`: файл и дословная цитата, в которой лежит ответ. Фрагмент
считается «правильным», если он из этого файла и содержит цитату. По списку,
который вернул поиск, считаются три метрики:
- **recall@k** — какая доля нужных цитат попала в первые k фрагментов (для
  многошагового вопроса надо найти все части);
- **MRR** — насколько высоко первый правильный фрагмент (1 — на первом месте,
  1/3 — на третьем);
- **nDCG@k** — то же, но учитываются все правильные фрагменты, и чем выше,
  тем больше вклад.

Так видно, кто виноват в плохом ответе: если recall низкий, нужного текста не
было в контексте (виноват поиск), а если высокий — ошибся генератор.

**Вопросы без ответа.** В наборе есть 6 вопросов, ответа на которые в базе нет
(например, про несуществующую модель NW-300). Правильное поведение здесь —
честно сказать «не знаю». Отчёт показывает долю таких честных отказов и долю
ложных отказов на вопросах, где ответ есть.

**Абляции** (`scripts/run_ablation.py`) прогоняют набор на разных
конфигурациях: только вектор, только BM25, гибрид, гибрид + HyDE, гибрид +
реранкер, полный агент, и на разных моделях эмбеддингов. Итоговая таблица
лежит в `results/ablation.md`.

## Часть 7. Полный путь одного вопроса (соберём всё вместе)

Вопрос: **«Мы на тарифе Enterprise с манипуляторами NW-200. Какой лимит API и
какая компенсация, если тикет об остановке продакшена нарушит SLA?»**

1. **Планировщик** видит, что вопрос составной, и разбивает: (а) лимит API для
   Enterprise; (б) компенсация при нарушении SLA на Sev 1.
2. **Агент** вызывает `search("лимит API Enterprise AtlasControl")`.
3. **Гибридный поиск**: векторный + BM25 (тут BM25 ловит точное «NW-200»,
   «AtlasControl»), объединяет через RRF → 10 кандидатов.
4. **Реранкер** оценивает их, лучшие — из `product_specs.md` (9/10).
5. **Агент** видит высокие оценки, но второй части про SLA ещё нет → вызывает
   `search("компенсация при нарушении SLA Sev 1")`.
6. Снова поиск+реранк → лучшие из `support_sla.md`.
7. **Агент** решает: данных по обеим частям достаточно → останавливается.
8. **Генератор** пишет ответ по фрагментам: «Лимит — 6 000 запросов/мин;
   компенсация — 5% от месячной платы за инцидент, не более 25%», с дословными
   цитатами из обоих документов.
9. **Проверка достоверности**: «всё подтверждено фрагментами» → обоснованность
   высокая, уверенность высокая.
10. Пользователь получает ответ + ссылки на `product_specs.md` и `support_sla.md`.

Один наивный RAG-поиск тут, скорее всего, нашёл бы только что-то одно. Агентный
подход добывает **оба** факта.

## Часть 8. Мини-словарь терминов

- **RAG** — поиск нужных фрагментов + ответ модели строго по ним.
- **Чанк (chunk)** — небольшой фрагмент документа, единица поиска.
- **Эмбеддинг (embedding)** — представление текста в виде вектора чисел, где
  близость = смысловая похожесть.
- **Вектор** — список чисел; «координаты текста» на «карте смыслов».
- **Косинусная близость** — мера того, насколько два вектора «смотрят в одну
  сторону» (насколько тексты похожи).
- **BM25** — классический поиск по ключевым словам.
- **Гибридный поиск** — смысловой + ключевой одновременно.
- **RRF (Reciprocal Rank Fusion)** — способ честно объединить два рейтинга по
  местам, а не по несравнимым баллам.
- **HyDE** — поиск по «выдуманному гипотетическому ответу» вместо короткого
  вопроса.
- **Реранкинг** — пересортировка кандидатов моделью по реальной полезности.
- **CRAG (Corrective RAG)** — оценка качества найденного и переформулировка
  запроса при плохих результатах.
- **Галлюцинация** — уверенно сказанный, но выдуманный/неверный ответ модели.
- **Обоснованность (faithfulness)** — доля утверждений ответа, реально
  подтверждённых найденными фрагментами.
- **Цитата / ссылка (citation)** — указание, из какого фрагмента взят факт.
- **Структурированный вывод** — ответ модели в строгом формате (JSON по схеме).
- **Tool-use loop (цикл с инструментом)** — модель сама вызывает «инструменты»
  (здесь — `search`) столько раз, сколько нужно.
- **Агентный RAG** — RAG, где моделью управляется сам процесс поиска
  (многошаговый, самокорректирующийся).

---

## Итог

AtlasRAG — это не «поиск + один запрос к модели». Это управляемый Claude процесс:
**понять вопрос → искать двумя способами → оценить найденное → при необходимости
искать ещё → ответить строго по источникам → проверить себя на честность**. Такой
конвейер даёт ответы, которым можно доверять в бизнесе: с источниками, с
честной оценкой уверенности и с защитой от выдумок.
